## Рекомендуемая реализация

Сделай решение учебным, автономным и проверяемым без реального API там, где возможно.

### 1. Локальный подсчёт токенов до запроса

Добавь отдельный файл, например `token_counter.go`.

Реализуй простой локальный счётчик токенов без внешних зависимостей. Для учебного задания допустима приближённая оценка, но это нужно явно назвать в README.

Минимальный вариант:

- считать слова, числа, знаки препинания и CJK/кириллические фрагменты;
- учитывать служебную стоимость каждого chat message;
- считать отдельно:
  - токены текущего user prompt;
  - токены сохранённой истории;
  - токены system message;
  - токены полного prompt payload;
  - токены ответа модели, если ответ уже получен;
  - общий total.

Хорошая структура:

- `TokenCounter` или функции `EstimateMessageTokens`, `EstimateMessagesTokens`;
- `TokenBreakdown`;
- `TokenReport`.

Не полагайся только на `usage` от API, потому что задание просит считать токены в коде агента и показывать ситуацию до переполнения.

### 2. Лимит контекста

Добавь в конфигурацию лимит контекста, например:

- `defaultContextLimit`;
- CLI-флаг `-context-limit`;
- env `DAY8_CONTEXT_LIMIT`.

Перед HTTP-запросом агент должен оценить полный prompt: `system + history + current user`.

Если оценка превышает лимит, агент должен вернуть понятную ошибку до обращения к API. В ошибке покажи:

- оценку токенов;
- лимит;
- насколько превышен лимит;
- что именно занимает место: system/history/current request.

Это нужно для демонстрации “что ломается при переполнении”. Можно также оставить реальный API error handling, но локальная ошибка проще и стабильнее для тестов.

### 3. Метрики в ответе агента

Расширь `AgentResponse`:

- добавь локальный token report;
- сохрани `Usage` от API как фактические токены;
- добавь estimated answer tokens после получения ответа;
- добавь finish reason.

CLI должен печатать:

- ответ модели в stdout;
- в stderr компактную таблицу/блок:
  - current request tokens;
  - history tokens;
  - system tokens;
  - estimated prompt tokens;
  - estimated answer tokens;
  - estimated total tokens;
  - API usage, если пришёл;
  - context limit и remaining tokens.

### 4. Web-интерфейс

В web API верни token report вместе с ответом.

В `chat_page.html` покажи под ответом компактные метрики:

- запрос;

- ответ;
- всего;
- лимит/остаток.

При ошибке переполнения покажи её в UI как понятное сообщение.

Не перегружай интерфейс. Это учебный чат, не аналитическая панель.

### 5. Демонстрации короткого, длинного и переполненного диалога

Добавь отдельный режим CLI, например:

- `-demo-tokens`;
- или отдельный файл/команда внутри текущего `main`.

Демо должно работать без реального API, чтобы тестировать и показывать рост токенов стабильно.

Сценарии:

- short: 1-2 коротких сообщения;
- long: серия сообщений, где история растёт;
- overflow: искусственно длинная история или маленький `-context-limit`, чтобы показать превышение.

Вывод демо:

```text
Scenario: short
turn current history prompt answer total remaining status
1    8       0       24     12     36    7964      ok
2    10      20      46     15     61    7939      ok

Scenario: overflow
...
status: context limit exceeded
```

Важно показать именно динамику: с каждым ходом история увеличивает prompt tokens и стоимость следующего запроса.
