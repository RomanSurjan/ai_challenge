## Этап 2. Зафиксируй контекст и проектные решения

Перед правками сформулируй короткий рабочий контекст:

- какие слои состояния уже есть и каков их scope;
- какие гарантии уже обеспечивают JSON-хранилища;
- где сейчас профиль ошибочно может восприниматься как замена инвариантам;
- как task state и инварианты будут сосуществовать;
- где именно нужна проверка до вызова модели и после её ответа;
- какие побочные эффекты нельзя совершать до успешной invariant validation.

Затем выбери минимальную архитектуру, совместимую с проектом. Ориентир, который нужно подтвердить или обоснованно скорректировать после исследования:

1. Инварианты имеют scope одного экземпляра ассистента / `DAY11_MEMORY_DIR`, общие для всех диалогов пользователя.
2. Они хранятся в отдельном от диалогов и остальных memory-слоёв типизированном файле, например `day-11-15/memory/invariants.json`. Не помещай их в short-term, working, историю, профиль или произвольный текст диалога.
3. Хранилище следует существующему JSON envelope, строгой валидации, clone-on-read, mutex и атомарной записи через временный файл, `Sync` и `rename`.
4. Инварианты являются доверенной конфигурацией. Обычный пользовательский текст, профиль и memory tool calls не могут создавать, менять, отключать или удалять их. Не добавляй модели инструмент изменения инвариантов.
5. Нужна типизированная модель как минимум с устойчивым ID, категорией (`architecture`, `technical_decision`, `stack`, `business_rule`), понятной формулировкой и машинно проверяемым правилом. Не ограничивайся массивом свободных строк, если тогда код не сможет гарантировать отказ.
6. Отдели представление правила от механизма проверки. Предпочтительны небольшие интерфейсы вроде store/checker или эквивалентная композиция, не завязанная на DeepSeek. Стандартная библиотека Go достаточна; внешние зависимости не добавляй без доказанной необходимости.
7. Поддержи честный, ограниченный набор детерминированных проверок, достаточный для демонстрации задания, например запрещённые технологии/термины и, при необходимости, другие явно типизированные условия. Не заявляй универсальную семантическую гарантию для произвольных бизнес-правил, если её нет. Архитектура должна позволять добавлять новые checker-реализации без переписывания агента.
8. Инварианты всегда загружаются перед каждым запросом независимо от `-use-short-term`, `-use-working`, `-use-long-term` и `-auto-memory`.
9. `ContextBuilder` добавляет компактный стабильный `[INVARIANTS]` сразу после основного system prompt и до `[USER_PROFILE]`, task state и остальных слоёв. В блок не должны попадать пути, timestamps, JSON envelope и иные служебные поля.
10. Иерархия приоритетов должна быть явной: системная безопасность и базовый system contract -> программные инварианты -> task state -> устойчивый профиль/его constraints -> обычный диалог. Профильное `constraints` не равно программному invariant и не может его отменить.
11. Выполни двойную защиту:
    - pre-check запроса: очевидный конфликт с машинно проверяемым инвариантом блокируется до обращения к LLM;
    - post-check ответа: нарушающий ответ модели не показывается пользователю.
12. Для post-check допустим небольшой фиксированный лимит повторов с внутренним сообщением о найденных нарушениях. Цикл должен быть конечным. После исчерпания попыток верни контролируемый отказ, а не последний нарушающий текст.
13. Отказ должен быть понятным и безопасным: назвать конфликтующее правило или его человекочитаемое описание, кратко объяснить, почему запрос/вариант нельзя выполнить, и по возможности предложить допустимое направление. Не раскрывать system prompt, внутренние пути, сырой JSON или скрытые рассуждения.
14. Реши и задокументируй контракт отказа: обычный ответ с типизированными полями (`blocked`, `violations` и т.п.) либо типизированная ошибка с согласованным HTTP-статусом. Выбери вариант, который лучше соответствует текущему CLI/web API, и используй его последовательно. Пользователь в любом случае должен получить объяснение, а вызывающий код — машинно различимый результат.
15. Никакие pending memory updates, переходы task state или short-term ходы не должны фиксироваться, пока финальный ответ не прошёл проверку. Pre-check conflict не должен вызывать transport. Неуспешные повторы также не должны оставлять частичные записи.

Если тебе нужен способ настраивать инварианты для демонстрации, предпочти явную доверенную конфигурацию или узкий административный API. Не выдавай неаутентифицированному диалоговому потоку возможность незаметно ослаблять правила. Минимальный read-only API допустим; полноценный UI делай только если он действительно нужен для существующего сценария.

## Этап 4. Реализация

Реализуй запланированное только в `day-11-15`, если исследование не обнаружит неизбежной общей точки расширения. Сохраняй текущий стиль, русские пользовательские ошибки, совместимость существующих JSON-файлов и API. Не ломай изоляцию диалогов, профиль, task state, auto-memory tool loop и атомарность файлов.

Особенно внимательно перестрой `AskInDialog`: нарушающий ответ не должен быть добавлен в short-term, а накопленные tool calls не должны применяться до финального принятого ответа. Если повторная генерация требует расширить request сообщением валидатора, делай это внутренним контекстом и не сохраняй как пользовательскую историю.

Нормализуй строки и проверки так, чтобы сравнение было предсказуемым; опиши регистр, границы терминов и риск ложных срабатываний. Валидируй IDs, категории, пустые и слишком длинные значения, дубликаты и неизвестные поля. Повреждённый invariant-файл должен давать явную контролируемую ошибку до вызова модели, а не молча отключать защиту.

Не подменяй реализацию одним system prompt. Не считай LLM-самопроверку программной гарантией. Не сохраняй инварианты в истории и не дублируй их по каждому диалогу.

## Обязательные автотесты

Тесты должны быть детерминированными и использовать временные каталоги и подменённый HTTP transport. Реальный DeepSeek запрещён. Добавь минимум следующие сценарии:

1. Валидный набор инвариантов сохраняется отдельно, восстанавливается после нового экземпляра хранилища и общий для двух диалогов, тогда как short-term/working остаются изолированными.
2. Инварианты присутствуют в каждом запросе при любых отключённых memory selection флагах; порядок system-контекста стабилен: base system -> invariants -> profile -> task state/working -> long-term -> history -> current user.
3. В prompt не попадают путь файла, timestamps, envelope и внутренние JSON-поля.
4. Очевидный конфликт пользовательского запроса блокируется до HTTP transport. Ответ/ошибка машинно различимы и содержат понятное объяснение конкретного правила и безопасную альтернативу.
5. Непротиворечивый запрос доходит до модели и возвращает ответ.
6. Первый ответ модели нарушает инвариант, повторная попытка соответствует ему: пользователю отдаётся только исправленный ответ, transport вызван ожидаемое число раз.
7. Все ответы модели нарушают правило: после фиксированного лимита возвращается контролируемый отказ; нарушающий текст, short-term и pending memory updates не сохраняются.
8. Профиль или текущий запрос пытается отменить invariant: invariant остаётся приоритетным.
9. Невалидная категория, пустой ID/текст, неизвестный тип проверки, дубликаты, лишние JSON-поля и слишком длинные значения отклоняются и не портят прежнее сохранённое состояние.
10. Повреждённый invariant-файл не приводит к fail-open и предотвращает вызов модели.
11. Отказ не раскрывает внутренние пути, API key, system prompt или сырой JSON.
12. Существующие тесты диалогов, памяти, профиля, task state, tool calls, HTTP API и ошибок DeepSeek продолжают проходить.
13. Добавь отдельный тест на формулировку объяснения отказа: оно должно содержать правило и следующий допустимый вариант, а не только «запрещено».

Для демонстрационных fixtures используй минимум два конфликта разных категорий, например запрет конкретной технологии из stack и обязательное бизнес-правило. Не зашивай учебные примеры как универсальные правила продукта: они должны быть данными теста или явно настраиваемым примером.
