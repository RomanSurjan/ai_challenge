## Что уже реализовано в Day 11

Сначала проверь эти сведения по актуальному коду, не принимай их вслепую:

- `memory.go` реализует три слоя памяти: short-term, working и long-term.
- Short-term и working memory изолированы по диалогам.
- Long-term memory общая для одного пользователя и всех его диалогов.
- В `LongTermMemory` уже есть `Profile []ProfileEntry`, но это только произвольные пары `key/value` без явной схемы предпочтений.
- `MemoryLayers.UpsertProfile` сохраняет такие пары в `long_term.json`.
- `POST /api/memory/long-term/profile` уже позволяет записывать одну пару `key/value`.
- `ContextBuilder` сейчас помещает профиль внутрь общего блока долговременной памяти.
- Профиль попадает в запрос только при включённом `LongTerm`/`-use-long-term`; следовательно, требование «подключить профиль к каждому запросу» сейчас не гарантируется.
- Порядок контекста сейчас: основной system prompt → working memory → вся long-term memory → история выбранного диалога → текущий запрос.
- Обычный текст пользователя намеренно не записывается автоматически в working или long-term memory.
- Тесты используют подменённый HTTP transport и не обращаются к реальному DeepSeek.
- В web-интерфейсе пока нет отдельного понятного редактора профиля.

Сохрани существующие свойства системы: изоляцию диалогов, атомарное JSON-хранилище, обработку повреждённых файлов, явную запись долговременной памяти и отсутствие реальных сетевых запросов в автотестах.

## Требования к проектированию

### 1. Scope профиля

Для текущего учебного приложения базовое ожидаемое решение — один профиль текущего пользователя на один каталог `DAY11_MEMORY_DIR`, общий для всех его диалогов. Это соответствует существующему scope long-term memory.

Не добавляй авторизацию и полноценную multi-user систему без доказанной необходимости. Для проверки «разных профилей» можно создавать два независимых memory store/Agent в тестах и использовать два временных каталога. Если после исследования выберешь другой scope, сначала обоснуй его и не допускай утечки профиля между пользователями.

### 2. Явная модель персонализации

Не оставляй критичные предпочтения неограниченным набором случайных ключей без контракта. Нужна типизированная или строго нормализованная модель профиля. Минимально она должна выражать:

- имя или обращение к пользователю — опционально;
- язык ответа;
- стиль/тон: например, формальный или разговорный;
- уровень подробности: краткий или подробный;
- формат: например, обычный текст, список или пошаговый ответ;
- устойчивый контекст пользователя: роль, уровень опыта или цель — опционально;
- список ограничений, которые должны учитываться в каждом ответе.

Конкретные enum и названия полей выбери после изучения текущего кода. Не раздувай схему. Для неизвестных значений, пустых строк, чрезмерно длинных полей и слишком большого количества ограничений должна быть понятная валидация.

Определи семантику конфликтов:

- основной system prompt, безопасность и программные инварианты всегда выше профиля;
- профиль является декларативными данными, а не произвольным способом внедрить новые system-команды;
- стиль и формат — настройки по умолчанию;
- ограничения профиля применяются устойчиво, пока пользователь явно не изменит сам профиль;
- текущий запрос не должен молча отключать обязательное ограничение фразой вроде «игнорируй профиль».

Не смешивай в одно поле мягкие предпочтения и жёсткие ограничения.

### 3. Хранение и совместимость

Профиль должен храниться в долговременной памяти и переживать перезапуск. Новые диалоги не должны создавать копии профиля или терять его.

Если меняется JSON-схема `long_term.json`, предусмотрите безопасную загрузку старого формата. Возможные варианты: миграция прежних `ProfileEntry`, временная поддержка обеих схем или явная версия данных. Не удаляй существующие данные пользователя и не применяй молчаливую потерю полей.

Сохранение должно остаться атомарным через существующий store. Обычные сообщения пользователя не должны автоматически менять профиль: в этом задании «автоматически учитывает» означает автоматическую инъекцию сохранённого профиля, а не скрытое извлечение предпочтений из каждого сообщения.

### 4. Подключение к каждому запросу

Сделай профиль отдельным компактным system-блоком с однозначной разметкой. Не передавай служебный JSON напрямую и не смешивай профиль с решениями/знаниями так, чтобы модель не различала их назначение.

Рекомендуемый порядок сообщений:

1. основной system prompt;
2. блок персонализации пользователя;
3. релевантная working memory;
4. остальные выбранные long-term решения/знания;
5. short-term история выбранного диалога;
6. текущий запрос пользователя.

Ключевое требование: `-use-long-term=false` может отключать решения и знания, но не должен незаметно отключать обязательную персонализацию. Профиль загружается и применяется отдельно при каждом `Ask`/`AskInDialog`.

Не добавляй пустой или шумный блок, если профиль ещё не настроен. Для отсутствующего профиля определи нейтральное и документированное поведение. Обновление профиля должно влиять уже на следующий запрос без перезапуска.

Не допускай, чтобы текст профиля выдавался пользователю как часть ответа или чтобы профиль мог переопределить основной system prompt. Формат блока должен явно объяснять модели, что это декларативные предпочтения текущего пользователя.

### 5. Внешний контракт настройки

Должен быть понятный способ:

- получить текущий профиль;
- создать или полностью обновить профиль;
- при необходимости частично обновить отдельное поле;
- получить `400` на некорректные значения;
- отличить отсутствие профиля от ошибки повреждённого хранилища.

Развивай существующий API аккуратно. Сохрани обратную совместимость `POST /api/memory/long-term/profile`, если она разумна; если контракт меняется, явно задокументируй миграцию. Не создавай несколько пересекающихся endpoint без необходимости.

Добавь минимальный пользовательский способ настройки, соразмерный приложению: API с понятными примерами обязателен; компактный web-редактор профиля желателен, если он не раздувает задачу и согласуется с текущим интерфейсом. CLI-флаги не нужны, если API/web уже полностью покрывают сценарий.

### 6. Контроль размера контекста

Профиль должен быть коротким и детерминированным. Не дублируй его в нескольких system-сообщениях и не добавляй нерелевантные данные. Порядок полей должен быть стабильным, чтобы тесты и поведение не зависели от map iteration.

## Обязательные проверки

Автотесты не должны зависеть от реального API или вероятностного текста модели.

Добавь тесты минимум на следующие сценарии:

1. Валидный профиль сохраняется и полностью восстанавливается после создания нового `MemoryLayers` на том же каталоге.
2. Профиль общий для всех диалогов одного пользователя, но short-term и working memory по-прежнему изолированы.
3. Два агента с двумя независимыми профилями получают один и тот же user prompt, но формируют разные system-контексты без взаимной утечки.
4. Подменённый transport читает отправленные `messages` и возвращает разные фиксированные ответы в зависимости от профиля. Это детерминированно доказывает путь «профиль → запрос → различающийся ответ».
5. Профиль присутствует в каждом запросе, даже если обычная long-term memory отключена.
6. Обновление профиля меняет следующий запрос.
7. При пустом профиле нет пустого/сломавшегося system-блока и сохраняется нейтральное поведение.
8. Невалидные enum, пустые обязательные значения, слишком длинные значения и лишние JSON-поля возвращают понятную ошибку и не портят сохранённый профиль.
9. Существующий старый `long_term.json` загружается без потери решений и знаний.
10. Порядок контекста стабилен, служебный JSON и внутренние пути не попадают в prompt.
11. Ошибка DeepSeek по-прежнему не сохраняет неуспешный ход.
12. Существующие тесты диалогов, памяти и HTTP API продолжают проходить.

Для ручной A/B-проверки опиши в README воспроизводимый сценарий:

- профиль A: кратко, формально, обычный текст, без примеров кода;
- профиль B: подробно, дружелюбно, пошаговый список, с примерами;
- одинаковый вопрос для обоих профилей;
- ожидаемые наблюдаемые различия по длине, тону, структуре и наличию примеров.

Чтобы не смешивать историю и профиль, используй два независимых каталога памяти или другой явно изолированный способ, соответствующий выбранному scope. Реальный вызов DeepSeek оставь только как необязательную ручную проверку.
