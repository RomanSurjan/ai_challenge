# Day 11: память, персонализация и конечный автомат задачи

Day 11 поддерживает несколько диалогов, сохраняет выбранный диалог между запусками, автоматически подключает долговременный профиль пользователя к каждому запросу и позволяет модели предложить полезные обновления working и long-term памяти. Запись выполняет приложение через проверяемые API или tool calls; текст «я запомнил» сам по себе ничего не сохраняет.

## Архитектура

Используется общий типизированный индекс диалогов и отдельные JSON-файлы памяти каждого диалога:

```text
day-11-15/memory/
├── dialogs.json
├── long_term.json
├── invariants.json
├── .turn_transaction.json   # только пока turn-commit подготовлен/восстанавливается
└── dialogs/
    ├── dlg-<hex>/
    │   ├── short_term.json
    │   └── working.json
    └── dlg-<hex>/
        ├── short_term.json
        └── working.json
```

`dialogs.json` содержит `active_dialog_id` и массив метаданных: устойчивый `id`, отображаемое `title`, `created_at`, `updated_at`. ID генерируется локально из криптографически случайных байтов в формате `dlg-<hex>`, валидируется при каждом внешнем обращении и только он используется в файловом пути. Название в путь не попадает. Название по умолчанию — детерминированное `Диалог N`; модель для него не вызывается. Единственный типизированный профиль хранится как `user_profile` в общем `long_term.json`.

Такой вариант выбран вместо одного общего файла всех историй, потому что повреждение short-term или working одного диалога не ломает остальные, а небольшого общего индекса достаточно для списка и active state. Отдельные файлы без индекса потребовали бы восстанавливать метаданные сканированием каталогов. Один каталог на диалог удобен для dialog-scoped working memory.

Каждый постоянный JSON-файл имеет типизированную структуру, `version`, `data` и `updated_at`. Сохранение валидирует данные, пишет временный файл в том же каталоге, вызывает `Sync` и атомарно заменяет цель через `rename`. Временные файлы и журнал транзакции не являются слоями памяти и никогда не попадают в model prompt, HTTP-ответы или `memory_updates`.

## Область действия памяти

| Слой | Scope | Содержимое | Запись |
| --- | --- | --- | --- |
| Краткосрочная | отдельная для каждого диалога | успешные пары `user/assistant` | автоматически после успешного ответа DeepSeek |
| Рабочая | отдельная для каждого диалога | `goal`, `status`, `notes`, `results` текущей задачи | автоматически по tool call модели или явным working API |
| Долговременная | общая для пользователя и всех диалогов | типизированный пользовательский профиль, совместимые `profile` key/value, `decisions`, `knowledge` | автоматически по tool call модели или явным long-term API |
| Инварианты | общие для экземпляра ассистента / `DAY11_MEMORY_DIR` | архитектура, технические решения, стек и бизнес-правила | только доверенная конфигурация хоста; модель и chat API изменять их не могут |

Working memory сделана dialog-scoped: отдельная беседа обычно соответствует отдельной текущей задаче, поэтому цель и промежуточные данные одной задачи не должны попадать в другую. Общая working memory была бы проще, но смешивала бы задачи после переключения диалогов. Long-term остаётся общей, потому что устойчивый профиль и знания пользователя нужны во всех беседах и не должны дублироваться.

Обычный пользовательский текст не копируется в working или long-term автоматически. Модель получает узкие инструменты и должна решить, пригодится ли конкретная информация позже:

- working — только цель, статус, заметка или промежуточный результат текущей задачи выбранного диалога;
- profile — устойчивое предпочтение или факт профиля пользователя;
- decisions — действительно принятое решение;
- knowledge — проверенное или явно сообщённое знание, полезное в будущих диалогах;
- временные подробности, догадки, секреты и чувствительные данные не сохраняются.

Short-term не является инструментом модели: успешная пара `user/assistant` по-прежнему добавляется приложением после полностью успешного финального ответа.

## Программные инварианты

Инварианты хранятся отдельно в `invariants.json`, а не в истории, working memory, профиле, decisions или knowledge. Каждый элемент содержит устойчивый `id`, категорию `architecture|technical_decision|stack|business_rule`, человекочитаемые `description` и `alternative`, а также машинное правило:

- `forbidden_terms` отклоняет текст, содержащий любой из перечисленных терминов;
- `required_terms` отклоняет текст, в котором отсутствует хотя бы один обязательный термин;
- `targets` задаёт область `request`, `response` или обе.

Сопоставление регистронезависимое, последовательности пробелов нормализуются, а буквенно-цифровые термины проверяются по границам слов: `Java` не срабатывает внутри `JavaScript`. Это намеренно ограниченная детерминированная проверка, а не универсальное понимание смысла.

Файл использует тот же envelope `version/data/updated_at`, но декодируется строго: неизвестные поля, неизвестные категории/типы/targets, пустые и слишком длинные значения, повторные ID и термины отклоняются. Замена набора сначала полностью валидируется, поэтому невалидный набор не затирает прежний. Повреждённый файл приводит к fail-closed ошибке до сетевого вызова.

Приоритет фиксирован: базовый system contract и безопасность → `[INVARIANTS]` → `[TASK_STATE]` → `[USER_PROFILE]` и его мягкие constraints → память и текущий диалог. Пользовательский текст, профиль и tool calls не могут ослабить или изменить инвариант; у модели нет такого инструмента.

Поток запроса выглядит так:

1. Загрузить инварианты и выполнить pre-check текущего сообщения до DeepSeek.
2. Добавить компактный `[INVARIANTS]` сразу после базового system prompt.
3. Получить черновик и накопить tool calls только в памяти процесса.
4. Выполнить post-check ответа. Нарушивший черновик пользователю не показывается.
5. Повторить генерацию с внутренней обратной связью валидатора, максимум три попытки суммарно.
6. После принятого ответа применить pending memory/task операции и записать short-term. При исчерпании попыток вернуть типизированный отказ и отбросить все pending операции.

Отказ реализован как `InvariantViolationError`; HTTP возвращает `409 Conflict`, `blocked: true` и массив `violations`. Текст называет правило, причину и допустимую альтернативу, но не раскрывает system prompt, ключи, пути или сырой JSON.

## Формализованное состояние задачи

Каждый диалог хранит собственное `task_state` внутри своего `working.json`; второго источника истины нет. Отсутствие поля означает, что задача ещё не начата, поэтому прежние файлы остаются совместимыми. Новая задача всегда создаётся на этапе `planning` и содержит:

- цель в dialog-scoped working memory;
- типизированный `stage`;
- `current_step` и `expected_action`;
- ортогональный флаг `paused`;
- полный план и типизированное подтверждение `plan_approved`;
- `validation_passed` и описание результата проверки;
- `updated_at`.

Старый `TaskStatus` теперь является только производным представлением: `planning` → `not_started`, активные `execution`/`validation` → `in_progress`, пауза → `blocked`, `done` → `completed`. Старый endpoint `working/status` не выполняет переходы и возвращает `409`, если запрошенный status не совпадает с FSM. Поэтому установить `completed` в обход валидации невозможно.

### Таблица переходов и guards

| Текущий этап | Разрешённый следующий этап | Обязательное условие |
| --- | --- | --- |
| `planning` | `execution` | план явно утверждён операцией approve-plan |
| `execution` | `planning` | утверждение прежнего плана сбрасывается |
| `execution` | `validation` | — |
| `validation` | `execution` | результат прежней валидации сбрасывается |
| `validation` | `done` | успешно зафиксирована валидация |
| `done` | нет | терминальное состояние |

Любой отсутствующий переход отклоняется типизированной ошибкой без изменения working memory или истории. Этап меняется только централизованным методом `Transition`; обновление шага и ожидаемого действия — отдельная операция. Автоматические task tool calls ограничены одним переходом за один пользовательский ход: второй переход считается FSM-конфликтом и отменяет весь пользовательский ход, включая первый pending-переход.

### Pause/resume

Пауза не является этапом. Её можно включить в `planning`, `execution` или `validation`; повторная пауза идемпотентна. Этап, шаг, ожидаемое действие, план и подтверждения сохраняются без изменений. Пока задача на паузе, FSM отклоняет переходы и изменение прогресса; разрешён только `resume`. `done` нельзя приостановить или возобновить.

После перезапуска `working.json` загружается вместе с точной позицией задачи. Даже при пустой short-term history модель получает отдельный системный блок `[TASK_STATE]` с целью, планом, этапом, шагом, ожидаемым действием, паузой, доступными переходами и правилом поведения текущего этапа.

## Контракт профиля

Типизированный профиль содержит опциональное обращение `name`, обязательные enum `language`, `tone`, `detail`, `format`, опциональный устойчивый `context`, отдельный массив `constraints` и служебный `updated_at`. Поддерживаются `ru|en`, `formal|friendly`, `concise|detailed`, `plain_text|bullets|steps`. Свободные поля ограничены по длине и одной строкой; допускается не более 10 непустых уникальных ограничений.

Тон, подробность и формат — мягкие настройки по умолчанию. `constraints` — устойчивые требования к ответу, но основной system prompt, безопасность и программные инварианты всегда выше профиля. Обычный текст сам по себе не заменяет типизированный профиль: полная настройка выполняется через профильный API или web-редактор. Совместимые старые пары `profile key/value` сохраняются отдельно; они не попадают в prompt как произвольные инструкции и преобразуются в рабочий профиль только при полном однозначном соответствии новой схеме.

## Tool calls и семантика записи

Используется OpenAI/DeepSeek-совместимый `POST /chat/completions`: запрос содержит `tools`; для обычного диалога применяется `tool_choice: "auto"`, а для общего набора явно распознанных task-команд — named tool choice конкретного task tool. После единственного принудительного вызова следующий model request получает `tool_choice: "none"` и формирует финальный ответ. Ответ модели может содержать `tool_calls`, а приложение возвращает результаты сообщениями с ролью `tool` и соответствующим `tool_call_id`. Команды не извлекаются из Markdown или XML; детерминированное распознавание применяется только к явным императивным командам жизненного цикла задачи, а вопросы и обычные сообщения остаются на `auto`.

Семь узких инструментов памяти: `memory_set_working_goal`, `memory_set_working_status`, `memory_add_working_note`, `memory_add_working_result`, `memory_upsert_profile`, `memory_add_decision`, `memory_add_knowledge`. Добавленные в Day 11 инструменты жизненного цикла задачи работают отдельно и не заменяют этот контракт памяти. JSON-аргументы декодируются с запретом неизвестных полей, проверяются на обязательность, длину, enum и признаки секретов. Проверка секретов различает безопасное название категории (`password reset`, `API key rotation`, `access token storage`) и значение, похожее на credential: присваивание/пару `имя: значение`, Bearer-токен, заголовок приватного ключа, длинный `sk-…` токен или номер банковской карты. Ни один инструмент не принимает путь, `dialog_id` или операцию над short-term/списком диалогов. Если у working memory уже есть формализованное состояние задачи, изменение legacy-полей `goal` и `status` дополнительно проходит guards этого состояния и не может обойти его переходы.

Политика и описания task tools требуют ровно одну явно запрошенную task-операцию за пользовательский ход: approve не выполняет автоматический переход, validation не выполняет автоматический `done`, а текстовый ответ без соответствующего tool call не считается изменением состояния. Модель обязана вызвать явно запрошенный task tool даже если ожидает отказ: только backend FSM проверяет guards, поэтому запрещённая операция получает типизированный `409`, а не текстовую имитацию отказа. Строковые task-поля имеют `minLength`/`maxLength` в model schema, но backend по-прежнему независимо проверяет тип, обязательность, trim, лимит и чувствительные данные. Для `task_pause` и `task_resume` предпочтителен пустой объект `{}`; совместимый ответ провайдера с отсутствующей строкой `arguments` нормализуется в `{}` только для этих двух действительно безаргументных инструментов. Для любого инструмента с параметрами пустые arguments остаются ошибкой.

Операция task tool сначала прогоняется на копии состояния. Любой невалидный task tool call (плохой JSON, неизвестное поле или этап, пустое или слишком длинное значение, секрет и другие ошибки схемы) немедленно прерывает пользовательский ход с ошибкой, совместимой с `ErrMemoryToolCall`. Нарушение FSM guard немедленно прерывает ход типизированным `TaskStateError`/`ErrTaskConflict`. В обоих случаях модель не получает возможность продолжить генерацию в том же ходе.

При таком отказе целиком отбрасывается накопленный `pending`: не записываются working memory, task state, профиль, решения, знания и short-term user/assistant пара. Для FSM-конфликта `POST /api/chat` возвращает `409 Conflict` с `current_stage`, опциональным `requested_stage`, `allowed_transitions`, `expected_action`, `reason` и актуальным `task_state`; ответ не содержит внутренних путей, сырых аргументов инструмента или секретов. Корректные операции по-прежнему применяются только после принятого непустого финального ответа модели.

Ошибка формата tool call имеет безопасную типизированную диагностику: имя разрешённого инструмента, `error_category` (`malformed_json`, `missing_field`, `unknown_field`, `invalid_type`, `trailing_json`, `invalid_value`, `too_long` или `sensitive`), имя поля и, когда применимо, JSON-тип. Для категории `sensitive` дополнительно возвращается безопасный `validation_rule`, например `credential_assignment` или `bearer_token`. Сырые arguments и значения полей в ошибке не сохраняются и не возвращаются. FSM guard остаётся отдельным `409` с `error_category: "fsm_conflict"` и `fsm_guard: true`; он не маскируется как ошибка формата памяти.

Валидные изменения накапливаются в памяти процесса и применяются только после корректного непустого финального ответа модели. Повторяющаяся идентичная операция применяется один раз. За пользовательский запрос разрешено не более 4 tool-раундов и 8 memory calls; превышение лимита, неизвестный инструмент, плохие аргументы или ошибка последующего вызова DeepSeek отменяют все ещё не применённые изменения и не сохраняют short-term ход.

### Атомарный commit принятого хода

После принятого invariant-check ответа pending-операции, short-term пара и `updated_at` диалога фиксируются одной логической транзакцией. Она охватывает только реально изменяемые `working.json`/`long_term.json`, но всегда включает `short_term.json` выбранного диалога и `dialogs.json`.

Алгоритм:

1. Под общей блокировкой загружаются и валидируются исходные снимки затронутых слоёв.
2. Working/task и long-term mutations применяются только к копиям в памяти; одновременно готовятся новая short-term пара и метаданные диалога.
3. В `.turn_transaction.json` атомарно и с `Sync` сохраняются устойчивый `tx-…` ID, версия формата, состояние `prepared`, относительные пути и исходный/новый снимок каждой цели. Каталог синхронизируется.
4. Каждая цель заменяется через временный файл, `Sync`, `rename` и синхронизацию её каталога.
5. После фиксации всех целей journal атомарно переводится в durable-состояние `committed`. Затем он удаляется и каталог памяти снова синхронизируется; сбой только этой очистки безопасен. Лишь после durable commit-решения вызывающий код получает успешный `content` и фактически применённые недублирующиеся `memory_updates`.

При обычной ошибке до commit-решения координатор восстанавливает все исходные снимки в обратном порядке и возвращает контролируемую ошибку без успешного ответа. Если процесс остановлен между заменами, следующий `Initialize` или первое безопасное чтение на новом экземпляре обнаруживает journal: `prepared` откатывается к before-снимкам, а `committed` идемпотентно докатывается к after-снимкам. Recovery завершается до чтения состояния или вызова transport; неизвестный, повреждённый или содержащий недопустимую цель journal обрабатывается fail-closed.

Порядок блокировок один: `dialogMu → longTermMu → mutex конкретного JSON-файла`. Этот же `dialogMu` сериализует turn-commit, прямые working/task API, long-term/profile API и чтения внутри одного процесса, поэтому половина транзакции не наблюдается и параллельная запись не теряется.

## Создание и выбор диалога

На чистом первом запуске автоматически создаётся и выбирается `Диалог 1`. Создание следующего диалога делает его активным. Явный выбор сохраняется в `dialogs.json`, поэтому после перезапуска приложение продолжает активный диалог. Случайный диалог никогда не выбирается.

Пустой новый диалог не копирует историю или working memory предыдущего. Его memory-файлы могут отсутствовать до первой записи: отсутствие файла означает валидную пустую память.

## Сборка контекста

`ContextBuilder` не получает индекс, ID, пути или служебный JSON. `Agent` при каждом `Ask` заново загружает профиль независимо от выбранных слоёв, после чего сообщения формируются в порядке:

1. основной system prompt;
2. отдельная компактная политика автоматической памяти, если функция включена;
3. отдельный компактный `[INVARIANTS]`, если правила настроены;
4. отдельный `[TASK_STATE]`, если задача создана и working-слой выбран;
5. отдельный компактный `[USER_PROFILE]`, если профиль настроен;
6. непустой блок working memory выбранного диалога;
7. выбранные long-term решения и знания;
8. short-term история выбранного диалога;
9. текущее сообщение пользователя.

Если автоматическая память включена, сразу после основного system prompt добавляется отдельное компактное system-сообщение с политикой выбора слоя; основной prompt не изменяется. `-use-long-term=false` отключает решения и знания, но не профиль. Флаги `-use-short-term`, `-use-working`, `-use-long-term` и `-auto-memory` не отключают инварианты. При отсутствии профиля или инвариантов пустые system-блоки не создаются. Обновление применяется уже к следующему запросу без перезапуска. Служебный JSON, timestamps, пути и непроверенные legacy-пары в prompt не передаются.

После корректного непустого ответа DeepSeek успешный ход сохраняется только в выбранный диалог. HTTP-ошибка, сетевой сбой, некорректный JSON или пустой ответ ничего не добавляют.

## Миграция прежнего Day 11

Если `dialogs.json` ещё отсутствует, но в корне памяти есть прежние `short_term.json` и/или `working.json`, они валидируются и переносятся в `dialogs/dlg-legacy/`. Этот диалог становится первым и активным. `long_term.json` остаётся на прежнем общем месте.

Порядок миграции: сначала атомарно записываются dialog-scoped файлы, затем индекс. ID миграции детерминирован, поэтому прерывание до записи индекса и повторный запуск не создают дубликат. Старые файлы намеренно не удаляются как резервная копия; существующий индекс предотвращает повторный импорт. Повреждённый старый файл возвращает явную ошибку и не вызывает DeepSeek.

Старое поле-массив `profile` в `long_term.json` продолжает загружаться без потери решений и знаний. Из известных ключей (`language`, `tone/style`, `detail/verbosity`, `format/response_format`, `name`, `context`, `constraint`) типизированный профиль собирается только при наличии полного валидного набора. Неизвестные legacy-поля сохраняются, но не инъектируются в модель.

## Web-интерфейс

```bash
go run ./day-11-15 -serve
# или
./day-11-15/run_web.sh
```

Страница `http://localhost:8080` использует привычную двухколоночную компоновку чата. На широком экране слева постоянно находится боковая панель с кнопками `Новый диалог`, `Профиль ответов` и независимо прокручиваемым списком бесед; справа — название выбранного диалога, статус, история и поле отправки. Редактор читает текущий профиль, сохраняет полный валидный объект и сообщает, что изменения действуют со следующего запроса. Активная беседа выделена цветом и помечена `aria-current`, а каждый элемент списка является обычной кнопкой и доступен с клавиатуры.

Под названием диалога показан компактный индикатор этапа задачи и паузы. Рядом появляются только доступные действия: утверждение плана, разрешённые переходы, pause или resume. UI вызывает тот же строгий task API и не меняет этап локально.

На экранах уже 761 px список превращается в выезжающую панель. Она открывается кнопкой меню и закрывается после выбора, по затемнённой области или клавишей Escape. Основная область и поле отправки сохраняют всю доступную ширину без горизонтальной прокрутки.

Пользователь видит только `title`. Устойчивый `dialog_id` не показывается в списке, заголовке, сообщениях об ошибках или доступных подписях, но остаётся внутренним ключом API и файлового хранения. При выборе диалога frontend отправляет его ID серверу, очищает прежнюю визуальную историю и загружает только историю выбранного ID. Создание использует существующий `POST /api/dialogs` с пустым объектом: backend присваивает детерминированное имя `Диалог N`, а интерфейс автоматически выбирает новую пустую беседу.

Во время создания, переключения, загрузки истории и отправки конфликтующие действия блокируются. Если отправка не удалась, frontend перечитывает серверную историю выбранного диалога, поэтому незавершённый локальный ход не выглядит сохранённым. При исчезновении выбранного диалога список и серверный active dialog загружаются заново.

После фактически успешных автоматических записей под ответом агента появляется отдельная ненавязчивая подпись, например `Память обновлена: рабочая заметка, знание`. Она не является сообщением пользователя или агента и не появляется при отсутствии изменений, дубликате либо ошибке.

## HTTP API диалогов

Создать диалог:

```bash
curl -X POST http://localhost:8080/api/dialogs \
  -H 'Content-Type: application/json' \
  -d '{"title":"Исследование"}'
```

Ответ имеет HTTP `201` и явно содержит `dialog_id`. Пустой объект создаёт название `Диалог N`.

```bash
curl http://localhost:8080/api/dialogs
curl http://localhost:8080/api/dialogs/<dialog_id>
curl http://localhost:8080/api/dialogs/<dialog_id>/history

curl -X POST http://localhost:8080/api/dialogs/active \
  -H 'Content-Type: application/json' \
  -d '{"dialog_id":"<dialog_id>"}'
```

`GET /api/history` сохранён для обратной совместимости как история active dialog. Можно явно передать `?dialog_id=<id>`. Ответ истории содержит `dialog_id`.

Chat принимает явный ID или использует active dialog:

```bash
curl -X POST http://localhost:8080/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"dialog_id":"<dialog_id>","message":"Продолжим"}'
```

Успешный ответ всегда содержит `dialog_id` и может содержать безопасный список фактически применённых обновлений:

```json
{
  "dialog_id": "<dialog_id>",
  "content": "Продолжим с проверки API.",
  "memory_updates": [
    {"layer":"working","category":"notes","summary":"рабочая заметка"},
    {"layer":"long-term","category":"knowledge","summary":"знание"}
  ]
}
```

В `memory_updates` нет ID, путей, имён файлов, внутреннего JSON или полного содержимого записей. Поле отсутствует, если модель ничего не предложила или фактического изменения не произошло.

## HTTP API состояния задачи

Во всех запросах `dialog_id` можно опустить: тогда используется active dialog.

```bash
# Прочитать состояние. До создания задачи: started=false.
curl 'http://localhost:8080/api/task?dialog_id=<id>'

# Новая задача всегда начинается с planning.
curl -X POST 'http://localhost:8080/api/task?dialog_id=<id>' \
  -H 'Content-Type: application/json' \
  -d '{"goal":"Добавить FSM","current_step":"Составить план","expected_action":"Утвердить план"}'

curl -X POST 'http://localhost:8080/api/task/progress?dialog_id=<id>' \
  -H 'Content-Type: application/json' \
  -d '{"current_step":"Описать API","expected_action":"Согласовать API"}'

curl -X POST 'http://localhost:8080/api/task/approve-plan?dialog_id=<id>' \
  -H 'Content-Type: application/json' -d '{"plan":"1. Код 2. Тесты"}'

curl -X POST 'http://localhost:8080/api/task/transition?dialog_id=<id>' \
  -H 'Content-Type: application/json' -d '{"stage":"execution"}'

curl -X POST 'http://localhost:8080/api/task/validation?dialog_id=<id>' \
  -H 'Content-Type: application/json' \
  -d '{"passed":true,"details":"go test и go vet прошли"}'

curl -X POST 'http://localhost:8080/api/task/pause?dialog_id=<id>'
curl -X POST 'http://localhost:8080/api/task/resume?dialog_id=<id>'
```

Для прямого task API нарушение guard, действие во время паузы и запрещённый переход возвращают `409 Conflict`. Ответ содержит `current_stage`, `requested_stage`, `allowed_transitions`, `expected_action` и `reason`. Некорректный JSON или неизвестный этап возвращают `400`.

Если тот же guard срабатывает в task tool call внутри `POST /api/chat`, chat endpoint также возвращает типизированный `409` и добавляет актуальный `task_state`. Невалидный формат task tool call возвращается как контролируемая ошибка агента; в обоих случаях весь пользовательский ход откатывается и модель повторно не вызывается.

## HTTP API памяти

Dialog-scoped чтение:

```bash
curl 'http://localhost:8080/api/memory/short-term?dialog_id=<id>'
curl 'http://localhost:8080/api/memory/working?dialog_id=<id>'
```

Без query-параметра используется active dialog. Общая долговременная память:

```bash
curl http://localhost:8080/api/memory/long-term
```

Явная запись working memory выполняется для указанного или active dialog:

```bash
curl -X POST 'http://localhost:8080/api/memory/working/goal?dialog_id=<id>' \
  -H 'Content-Type: application/json' -d '{"value":"Реализовать API"}'

# Совместимый endpoint status только проверяет производное значение FSM.
# Он не выполняет переход и вернёт 409 при несовпадении.
curl -X POST 'http://localhost:8080/api/memory/working/status?dialog_id=<id>' \
  -H 'Content-Type: application/json' -d '{"value":"not_started"}'

curl -X POST 'http://localhost:8080/api/memory/working/notes?dialog_id=<id>' \
  -H 'Content-Type: application/json' -d '{"value":"Проверить изоляцию"}'

curl -X POST 'http://localhost:8080/api/memory/working/results?dialog_id=<id>' \
  -H 'Content-Type: application/json' -d '{"value":"Тесты проходят"}'
```

Long-term операции остаются общими:

```bash
# Прочитать типизированный профиль. Если его нет: configured=false, profile=null.
curl http://localhost:8080/api/memory/long-term/profile

# Создать или полностью заменить типизированный профиль.
curl -X PUT http://localhost:8080/api/memory/long-term/profile \
  -H 'Content-Type: application/json' \
  -d '{
    "name":"Роман",
    "language":"ru",
    "tone":"formal",
    "detail":"concise",
    "format":"plain_text",
    "context":"Go-разработчик",
    "constraints":["Не использовать примеры на Python"]
  }'

# Обратно совместимая запись одной legacy-пары key/value.
curl -X POST http://localhost:8080/api/memory/long-term/profile \
  -H 'Content-Type: application/json' -d '{"key":"language","value":"Russian"}'

curl -X POST http://localhost:8080/api/memory/long-term/decisions \
  -H 'Content-Type: application/json' \
  -d '{"statement":"Разделять истории","rationale":"Изоляция контекста"}'

curl -X POST http://localhost:8080/api/memory/long-term/knowledge \
  -H 'Content-Type: application/json' \
  -d '{"topic":"Memory","content":"Long-term общая"}'
```

Невалидные enum, пустые обязательные поля, превышение лимитов и лишние JSON-поля профиля возвращают `400` и не портят последнее корректное значение. Отсутствующий профиль — нормальный `200`, а повреждённый `long_term.json` — `500`. Ошибки ID/JSON возвращают `400`, неизвестный диалог — `404`, конфликт — `409`, ошибка DeepSeek — `502`, неподдерживаемый метод — `405`.

## Пример автоматического выбора памяти

Пользователь: «Для этой задачи сначала проверь миграцию. Во всех будущих проектах я предпочитаю краткие отчёты. В этом репозитории релизы выполняются по пятницам».

Модель до текстового ответа может вызвать:

1. `memory_add_working_note` для проверки миграции — только в текущем диалоге;
2. `memory_upsert_profile` для устойчивого предпочтения кратких отчётов — во всех диалогах;
3. `memory_add_knowledge` для явно сообщённого правила релизов — во всех диалогах.

Случайная просьба «покажи текущий файл» или собственная догадка модели не должна становиться долговременной памятью.

## Проверка изоляции и перезапуска

1. Открыть web-интерфейс: слева должен быть `Диалог 1`, без внутреннего ID.
2. Создать второй диалог и отправить другое сообщение.
3. Переключаться через боковую панель: active-состояние должно быть только у одного элемента, а история должна полностью меняться.
4. Уменьшить ширину окна: список должен открываться как выезжающая панель, не перекрывая composer в закрытом состоянии.
5. Остановить процесс и снова выполнить `-dialog-list`: `*` должен остаться у последнего выбранного диалога.
6. Отправить prompt без `-dialog`: он должен продолжить сохранённый active dialog.

Unit-тест `TestAgentBuildsDifferentRequestsForDifferentDialogs` перехватывает запросы без обращения к DeepSeek и доказывает, что один вопрос формирует разные `messages` из-за разных short-term и working данных.

### Ручная проверка FSM и продолжения после перезапуска

1. Создайте задачу через `POST /api/task`, но не утверждайте план.
2. Вызовите `POST /api/task/transition` с `{"stage":"validation"}`. Ожидается `409`, `current_stage: "planning"`, единственный допустимый следующий этап `execution`; `working.json` и история не меняются.
3. Утвердите план, перейдите в `execution`, обновите текущий шаг и остановите процесс.
4. Запустите приложение снова с тем же `DAY11_MEMORY_DIR` и выполните `GET /api/task`. Этап, план, шаг и ожидаемое действие должны совпасть с сохранёнными.
5. Очистите только `short_term.json` выбранного диалога и отправьте «Продолжай». В запрос модели всё равно попадёт `[TASK_STATE]`, поэтому повторно объяснять цель и план не требуется.
6. Поставьте задачу на паузу, перезапустите приложение, убедитесь в `paused: true`, затем выполните `resume`: восстановится тот же этап и шаг.

### Ручная проверка инвариантов

1. Сохраните приведённый выше `invariants.json` в выбранный `DAY11_MEMORY_DIR` и запустите сервер.
2. Отправьте `Используй Java`. Ожидается `409`, `blocked: true`, правило `stack-java`, объяснение и альтернатива на Kotlin; DeepSeek не вызывается.
3. Отправьте `Предложи реализацию на Kotlin`. Запрос должен дойти до модели.
4. Если модель всё же вернёт запрещённый термин, backend сделает не более двух повторов. При успешном исправлении в историю попадёт только исправленный ответ; иначе вернётся `409`, а история, pending memory updates и task state не изменятся.

## Ручная A/B-проверка профиля

Используйте два отдельных каталога `DAY11_MEMORY_DIR`, чтобы не смешивать профиль и историю.

1. Профиль A: `ru`, `formal`, `concise`, `plain_text`, ограничение «Не использовать примеры кода».
2. Профиль B: `ru`, `friendly`, `detailed`, `steps`, ограничение «Добавлять практический пример».
3. В новых диалогах задайте одинаковый вопрос: «Как организовать обработку ошибок в HTTP-клиенте?»
4. Ожидайте, что A будет короче, формальнее и без примера, а B — подробнее, дружелюбнее, пошагово и с примером.

Реальный DeepSeek нужен только для этой необязательной ручной проверки. Автотест использует два временных хранилища и подменённый transport, который читает `messages` и возвращает разные фиксированные ответы по профилю.

Профильные тесты отдельно доказывают сохранение после перезапуска, общий scope во всех диалогах, отсутствие утечки между двумя каталогами, инъекцию при `-use-long-term=false`, применение обновления к следующему запросу, нейтральное поведение без профиля, строгую API-валидацию, загрузку старого JSON и стабильный порядок system-контекста.

Тесты инвариантов покрывают отдельное персистентное хранилище, scope двух диалогов, порядок и чистоту prompt, pre-check без transport, post-check/retry, исчерпание попыток, отложенные memory/task эффекты, приоритет над профилем, строгую схему, fail-closed повреждение, две категории конфликтов и безопасное объяснение отказа.

Тесты транзакции инъектируют отказы первой записи, long-term, short-term и `dialogs.json`, сравнивают полные снимки до/после и после нового экземпляра, моделируют остановку после каждой целевой замены, rollback `prepared`, roll-forward `committed`, повторную recovery, повреждённый journal, успешный смешанный ход и конкурентные turn/API-записи. Production-флагов для отказов нет: тесты используют закрытый hook конкретного экземпляра и временные каталоги.

## Ограничения

- История передаётся целиком: нет summary или sliding window.
- Нет удаления, переименования, архивирования и ветвления диалогов.
- Нет авторизации и multi-user базы: один каталог памяти соответствует одному пользователю.
- Детерминированный checker гарантирует только явно описанные лексические правила. Перефразирование может обойти `forbidden_terms`, а `required_terms` подтверждает наличие слов, но не истинность утверждения. Для числовых, структурных и доменных правил нужны отдельные реализации `InvariantChecker`.
- Типизированный профиль не извлекается скрыто из обычного текста; legacy auto-memory сохранена отдельно для обратной совместимости.
- Нет векторного поиска, автоматического summary или семантического объединения похожих формулировок; устраняются только точные дубликаты и повторные tool calls.
- Защита от секретов сочетает инструкцию модели и консервативную серверную проверку известных признаков; она не заменяет полноценный DLP-классификатор.
- Turn-commit сериализован и восстанавливаем внутри одного процесса/каталога, но межпроцессной блокировки нет. Нельзя безопасно запускать несколько процессов, одновременно пишущих в один `DAY11_MEMORY_DIR`: journal устраняет crash-partial commit одного владельца, но не координирует конкурирующих владельцев каталога.
- Гарантия аварийного восстановления опирается на обычную семантику локальной файловой системы для `fsync` файла, атомарного `rename` в одном каталоге и `fsync` каталога. Ошибки записи и моделируемое завершение между стадиями покрыты; аппаратный сбой, который нарушает эти гарантии файловой системы, находится вне контракта.
