## Проверяемые задания

### Задание 1 — явная модель памяти

Нужно подтвердить наличие минимум трёх раздельных слоёв:

- краткосрочная память текущего диалога;
- рабочая память текущей задачи;
- долговременная память профиля, решений и знаний.

Проверь, что слои хранятся отдельно, имеют понятный scope, запись в них выполняется явно, а данные одного слоя не оказываются в другом без предусмотренной операции. Покажи, какие данные попадают в каждый слой и как включение или отключение слоя меняет запрос к модели и ответ агента.

### Задание 2 — персонализация

Нужно подтвердить наличие валидируемого профиля пользователя со стилем/тоном, форматом, подробностью, ограничениями и устойчивым контекстом. Профиль должен храниться долговременно, автоматически подключаться к каждому запросу, действовать во всех диалогах одного пользователя и не зависеть от включения обычных long-term решений и знаний.

Проверь минимум два независимых профиля на одном и том же запросе. Различие должно быть доказано детерминированно через перехваченный payload или подменённый transport, без реального API и без оценки вероятностного текста LLM «на глаз».

### Задание 3 — формализованное состояние задачи

Нужно подтвердить, что состояние содержит этап, текущий шаг и ожидаемое действие, хранится как типизированная структура и переживает перезапуск. Базовый жизненный цикл: `planning → execution → validation → done`.

Проверь паузу и продолжение на каждом незавершённом этапе. После восстановления состояния агент должен получать цель, план, этап, шаг и ожидаемое действие даже при пустой short-term истории, чтобы продолжить без повторного объяснения задачи.

### Задание 4 — инварианты

Нужно подтвердить отдельное от диалога и памяти хранилище инвариантов как минимум для категорий архитектуры, технических решений, стека и бизнес-правил. Инварианты должны иметь более высокий приоритет, чем профиль, состояние задачи, память и текущий запрос.

Проверь конфликт запроса с инвариантом до вызова модели, нарушение инварианта ответом модели после вызова, безопасный повтор генерации, исчерпание попыток, понятный отказ и отсутствие побочных записей при блокировке. Убедись, что пользователь, chat API и tool calls не могут менять или ослаблять доверенные инварианты.

### Задание 5 — контролируемые переходы

Нужно подтвердить явный конечный автомат с перечисленными состояниями, таблицей допустимых переходов и программными guards. Агент не должен перепрыгивать этапы.

Обязательно проверь:

- `planning → execution` запрещён без утверждённого плана;
- `planning → validation` и `planning → done` запрещены;
- `execution → validation` разрешён;
- `validation → done` запрещён без успешной зафиксированной валидации;
- возврат `execution → planning` сбрасывает устаревшее утверждение плана;
- возврат `validation → execution` сбрасывает устаревший результат валидации;
- `done` терминален;
- во время паузы запрещены переходы и изменение прогресса;
- legacy API статуса и tool calls не позволяют обойти FSM;
- после отклонённого перехода состояние и история не меняются;
- модель не может выполнить несколько переходов за один пользовательский ход.

## Критерии приёмки по слоям памяти

Для каждого слоя зафиксируй:

| Слой | Ожидаемый scope | Что допустимо хранить | Что нельзя хранить | Как записывается | Как влияет на контекст |
| --- | --- | --- | --- | --- | --- |
| short-term | один диалог | только успешные пары user/assistant | неуспешные ответы, другие диалоги | приложением после принятого ответа | история выбранного диалога |
| working | один диалог/одна текущая задача | goal, status, notes, results, task state | профиль и общие знания | явный API или проверенный tool call | контекст текущей задачи |
| long-term | один пользователь/каталог памяти | профиль, решения, знания | история отдельного диалога | явный API или проверенный tool call | устойчивый контекст всех диалогов |
| invariants | экземпляр ассистента/каталог памяти | доверенные неизменяемые правила | пользовательские заметки и профиль | только доверенная host-конфигурация | обязательный system-блок и программная проверка |

Проверь физическое разделение файлов, dialog scope, общий scope long-term и invariants, атомарную запись, строгую загрузку, поведение при повреждённом JSON и защиту от traversal через `dialog_id`.

## Обязательные негативные сценарии

Проверь или найди существующее детерминированное покрытие для следующих случаев:

1. Ошибка/пустой/невалидный ответ модели не добавляет short-term ход.
2. Невалидный, неизвестный, слишком длинный или содержащий секрет tool call ничего не записывает.
3. Ошибка после tool call отбрасывает pending memory/task operations.
4. Повторяющаяся операция не создаёт дубликат; лимиты tool rounds и операций соблюдаются.
5. Повреждение одного dialog-scoped файла не портит другие диалоги.
6. Профиль A не попадает в хранилище или запрос профиля B.
7. Текущий запрос «игнорируй профиль/инварианты» не меняет доверенные данные и не ослабляет приоритеты.
8. Конфликтующий request блокируется до transport; конфликтующий draft не показывается пользователю.
9. После исчерпания invariant retries не сохраняются история, память и task state.
10. Недопустимый переход возвращает типизированную ошибку/HTTP `409` с текущим этапом, допустимыми переходами, ожидаемым действием и причиной.
11. Пауза сохраняет точную позицию задачи; resume возвращает тот же этап и шаг.
12. Старый working/long-term JSON загружается или мигрируется без потери данных; неизвестное сохранённое состояние отклоняется безопасно.

## Правила выставления статуса

Для каждого подпункта используй только один статус:

- `PASS` — требование подтверждено кодом и воспроизводимым тестом/экспериментом;
- `PARTIAL` — основная часть есть, но остаётся конкретный функциональный или доказательный пробел;
- `FAIL` — требование нарушено или реализация допускает обход;
- `NOT VERIFIED` — проверить не удалось из-за конкретного внешнего блокера.

Не используй зелёный общий тестовый прогон как замену проверке требований. Не снижай оценку за явно документированные ограничения, которых нет в исходном задании, но укажи их отдельно как риски.
