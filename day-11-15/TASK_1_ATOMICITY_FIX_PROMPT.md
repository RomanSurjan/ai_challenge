## Найденный дефект

Один принятый пользовательский ход может изменять несколько файлов:

1. dialog-scoped `working.json`, включая `task_state`;
2. общий `long_term.json`;
3. dialog-scoped `short_term.json` с успешной парой user/assistant;
4. метаданные диалога в `dialogs.json` через обновление `updated_at`.

Сейчас `Agent.AskInDialog` сначала вызывает `applyPendingMemory`, а затем `AppendSuccessfulTurnToDialog`. Внутри `applyPendingMemory` working записывается раньше long-term. Поэтому ошибка на поздней записи оставляет раннюю запись на диске, хотя `AskInDialog` возвращает ошибку и пользователь не получает успешный ответ.

Дефект воспроизводится минимум так:

### Сценарий A — ошибка long-term после working

1. Подменённый transport возвращает в одном принятом ходе `memory_add_working_note` и `memory_add_knowledge`, затем корректный финальный ответ.
2. Working store успешно сохраняет заметку.
3. Long-term store принудительно возвращает ошибку записи.
4. `AskInDialog` возвращает ошибку.
5. Фактически working note уже сохранена, а short-term отсутствует.

### Сценарий B — ошибка short-term после pending memory

1. Подменённый transport возвращает валидный working или task tool call, затем корректный финальный ответ.
2. Pending working/task update успешно сохраняется.
3. Short-term store принудительно возвращает ошибку.
4. `AskInDialog` возвращает ошибку.
5. Фактически working/task state уже изменены, хотя успешного хода в истории нет.

README сейчас честно описывает отсутствие общей файловой транзакции. Для полного выполнения этого задания недостаточно документировать частичный commit: его нужно устранить.

## Требования к архитектуре исправления

Выбери минимальное решение, которое действительно обеспечивает all-or-nothing. Допустимые направления:

- небольшой транзакционный координатор с durable journal/WAL и восстановлением при инициализации;
- единое транзакционное представление принятого хода с последующим согласованным materialization слоёв;
- другое решение стандартной библиотекой Go, если оно даёт те же доказуемые гарантии.

Не добавляй внешнюю БД или dependency только ради удобства, если достаточно небольшого локального механизма.

Обязательные свойства решения:

1. Сначала загружаются и валидируются исходные снимки всех затрагиваемых слоёв.
2. Все mutations применяются к копиям в памяти. Ошибка в любой mutation не меняет постоянное состояние.
3. До commit известен полный набор новых значений и целевых файлов.
4. Транзакция охватывает только реально изменяемые файлы, но short-term успешного хода входит в ту же транзакцию всегда.
5. Если commit возвращает ошибку, текущее или автоматически восстановленное состояние эквивалентно состоянию до хода.
6. Если процесс остановился на середине commit, следующий `Initialize`/первое безопасное чтение завершает восстановление до выдачи состояния или сетевого вызова.
7. Повреждённый или неизвестный transaction journal обрабатывается fail-closed с понятной ошибкой; он не должен молча игнорироваться.
8. Journal, временные и backup-файлы не попадают в model prompt, HTTP-ответы и `memory_updates`.
9. Успешный commit не создаёт дубликаты при повторной recovery.
10. Для одной транзакции используется устойчивый ID и версия формата, если добавляется новый файл состояния.
11. Должен быть один документированный порядок mutex/locks. Не вызывай метод, повторно захватывающий уже удерживаемый mutex.
12. Не оставляй окно, в котором concurrent `AskInDialog`, прямой memory API или task API могут наблюдать или перезаписать половину транзакции внутри одного процесса.
13. Атомарность отдельного файла (`temp -> Sync -> rename`) сохраняется. Для durable journal учти синхронизацию самого файла и, если решение опирается на crash durability rename, каталога либо честно реализуй эквивалентное восстановление.
14. Не удаляй journal до того, как все целевые данные гарантированно зафиксированы.
15. После успешной транзакции `MemoryUpdates` отражает только фактически применённые недублирующиеся операции.

Если полная crash-atomicity на выбранной файловой модели требует компромисса, не скрывай его. Однако обычные ошибки записи и детерминированно моделируемое прерывание между стадиями commit должны восстанавливаться без частичного пользовательского хода.

## Обязательные regression tests

Все тесты должны использовать `t.TempDir`, подменённый transport и управляемые failing stores/hooks. Настоящий DeepSeek и внешняя сеть запрещены.

Добавь минимум следующие тесты:

1. **Working + long-term, отказ long-term.** Working успешно подготовлен, long-term падает. После ошибки и после нового экземпляра `MemoryLayers` working, long-term, short-term и task state равны снимкам до хода.
2. **Task state + long-term, отказ long-term.** Pending task transition или progress не остаётся после сбоя long-term.
3. **Short-term failure.** Pending working/task/long-term успешно подготовлены, но short-term падает. Ни один слой не остаётся изменённым после ошибки и перезапуска.
4. **Dialog metadata failure.** Ошибка обновления `dialogs.json` не оставляет новый ход или memory mutations частично применёнными.
5. **Ошибка на первой записи.** Никакой слой не меняется, journal корректно очищается или восстанавливается.
6. **Прерывание на каждой стадии commit.** Смоделируй подготовленный journal и остановку после каждой целевой замены; новый экземпляр хранилища должен детерминированно восстановить целостное состояние.
7. **Идемпотентная recovery.** Два последовательных запуска восстановления дают одно и то же состояние без дубликатов.
8. **Повреждённый journal.** Система fail-closed не вызывает transport и не изменяет память.
9. **Успешный смешанный ход.** Working note, task operation, long-term knowledge и short-term пара применяются ровно один раз; `memory_updates` корректен.
10. **Ошибка модели после tool call.** Существующая гарантия сохранена: pending не попадает в транзакцию.
11. **Invariant retry/exhaustion.** Черновики и их pending operations по-прежнему не фиксируются.
12. **FSM conflict.** Запрещённый переход по-прежнему возвращает типизированный `409`, не создаёт journal и не меняет состояние.
13. **Duplicate operations и лимиты.** Повторные операции не дублируются; лимиты tool rounds/operations не обходятся транзакцией.
14. **Concurrency/race.** Параллельные ходы и прямые API-операции не дают lost update или partial visibility; `go test -race` проходит.
15. **Совместимость.** Каталог без transaction journal и старые JSON-файлы загружаются как раньше.

Не считай тест достаточным, если он проверяет только отсутствие short-term. Для failure cases сравнивай полные снимки working, task state, long-term, short-term и dialog metadata до/после, затем повторяй проверку после создания нового экземпляра хранилища.

## Ошибки и внешний контракт

- Не раскрывай пользователю filesystem paths, содержимое journal, backup-файлы, сырые tool arguments, API key или внутренний JSON.
- Сохрани текущие безопасные HTTP-ошибки.
- Storage/transaction failure не должен возвращать успешный `content` или `memory_updates`.
- После восстановимой ошибки следующий запрос не должен видеть ghost note, ghost task transition, ghost knowledge или отсутствующую историю для уже применённых операций.
- Если recovery невозможна без вмешательства, верни явную fail-closed ошибку до transport и не продолжай поверх неоднозначного состояния.
