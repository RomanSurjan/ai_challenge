# Day 11 — линейный сценарий записи через web-чат

Этот сценарий заменяет API-ориентированную демонстрацию из `VIDEO_TEST_CASES.md`. Во время разделов 1–5 пользовательские действия выполняются только в web-интерфейсе и обычными сообщениями. Локальный mock сопоставляет естественные русские фразы с реальными memory/task tool calls; backend валидирует, применяет или отклоняет их. Реальный API и настоящий `DEEPSEEK_API_KEY` не используются.

## 0. Что подготовлено и как начать запись

Production-код и существующие тесты не изменены. Изолированный harness находится в `day-11-15/video-demo/`:

- `mock_server.py` — локальный детерминированный OpenAI-compatible transport; сохраняет только model payload, без заголовков;
- `prepare.sh` — собирает бинарник, создаёт только `/tmp/day11-web-demo.*`, именованные диалоги и доверенные demo-инварианты;
- `start.sh`, `control.sh` — запускают и перезапускают mock и шесть изолированных экземпляров;
- `clear-short-term.sh` — безопасно перемещает short-term ровно одного demo-диалога в backup под тем же `/tmp`;
- `restore-invariants.sh` — восстанавливает подготовленную доверенную копию demo-инвариантов;
- `smoke.sh` — короткий финальный набор тестов;
- `cleanup.sh` — останавливает процессы и удаляет только путь, совпадающий с `/tmp/day11-web-demo.*`.

До записи выполнить в терминале:

```bash
cd /Users/romansurzhan/ai_challenge
./day-11-15/video-demo/prepare.sh
./day-11-15/video-demo/start.sh
```

Открыть вкладки:

- основной экземпляр: `http://127.0.0.1:18110`;
- профиль A: `http://127.0.0.1:18112`;
- профиль B: `http://127.0.0.1:18113`;
- окружение без профиля: `http://127.0.0.1:18114`;
- изоляция повреждённого диалога: `http://127.0.0.1:18115`;
- повреждённые инварианты: `http://127.0.0.1:18116`.

Первые четыре адреса используют разные каталоги памяти. Все процессы обращаются только к mock на `127.0.0.1:18111`. Каталог `day-11-15/memory` не читается и не меняется.

### Важное ограничение текущего production UI

Web-чат показывает stage, pause, доступные кнопки, текст причины отказа и `memory_updates`, но не раскрывает все поля HTTP-ответа `blocked`, `violations`, `allowed_transitions`, `plan` и `validation_details` в отдельной панели. Успешные task tools компенсируют это безопасно: mock строит ответ из фактического JSON результата backend-инструмента. Для отказов mock не вызывается повторно, поэтому недоступные UI-поля нельзя честно «дорисовать» его текстом.

Поэтому следующие подпункты помечаются `UI BLOCKED`, хотя backend-контракт подтверждён автотестами:

- явное отображение `blocked: true` и массива `violations`;
- полный typed conflict с `current_stage`, `requested_stage`, `allowed_transitions`, `expected_action` и `reason`;
- числовой счётчик transport-вызовов до/после pre-check.

Минимальное возможное расширение без изменения production-кода — отдельный read-only demo proxy, который перехватывает тот же JSON и показывает эти поля рядом с чатом. В текущий harness он намеренно не включён: основное доказательство остаётся поведением штатного web-чата, а невидимые поля проверяются именованными тестами.

- **Фраза за кадром:** «Рабочая заметка применена backend-инструментом и остаётся в текущем диалоге.»
